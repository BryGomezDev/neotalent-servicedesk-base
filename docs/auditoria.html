Arquitectura

Cómo fluye un dato de principio a fin

La app tiene cuatro páginas HTML independientes. No hay bundler ni servidor: el navegador carga los archivos directamente. El estado se guarda en localStorage — el almacén del navegador que persiste entre recargas.

data/tickets.json ──fetch()──► state.tickets ──render*()──► DOM + localStorage ├── tickets-locales (tickets creados en el navegador) ├── tickets-estado (estado, historial, resolución) └── triaje-asignaciones (asignación por persona)

Archivos y sus responsabilidades (comprobadas)

/ ├── triaje.html ← página principal (Bandeja); carga ordenar.js y formato.js ├── nuevo-ticket.html ← formulario de creación; lógica 100 % inline ├── detalle-ticket.html ← detalle + historial; carga formato.js ├── cierre-ticket.html ← formulario de cierre; lógica 100 % inline ├── css/styles.css ← todos los estilos; cero media queries ├── data/tickets.json ← 60 tickets ficticios; sin datos reales ├── js/utils/ordenar.js ← ordenarPorPrioridad(); usada por triaje.html ├── js/utils/formato.js ← formatearFecha(); usada por triaje.html y detalle-ticket.html ├── js/utils/filtrar.js ← filtrarTickets(); solo la usan los tests de Node.js ├── js/app.js ← ⚠ HUÉRFANO: no lo carga ningún HTML └── js/components/ ← carpeta vacía (solo README.md, no hay archivos .js)

Seguridad

Lo que se publica y lo que se protege

SEC-00 Sin credenciales, API keys ni datos personales reales
Verificado ✓

Leídos todos los archivos .html, .js, .json y CLAUDE.md. No se encontró ninguna API key, contraseña, token, correo electrónico real ni dato de identificación personal. Los 60 tickets usan roles ficticios ("Jefe de turno", "Guardia de seguridad") y nombres de zona inventados.

SEC-01 Protección XSS correcta y consistente
Verificado ✓

Las cuatro páginas definen la misma función esc() que escapa los cinco caracteres HTML especiales antes de insertar texto externo en innerHTML. Los campos asignados con textContent son intrínsecamente seguros (el navegador no interpreta etiquetas en ellos).

triaje.html · l.166 
function esc(str) {
  return String(str)
    .replace(/&/g, '&amp;').replace(/</g, '&lt;')
    .replace(/>/g, '&gt;').replace(/"/g, '&quot;').replace(/'/g, '&#39;');
}
// Se usa en cada punto donde datos externos entran en innerHTML
Verificado en: triaje.html l.166, cierre-ticket.html l.148, detalle-ticket.html l.108

S2 Inyección CSS teórica via localStorage
Bajo

En triaje.html l.332, la variable asigColor se usa en un atributo style inline sin validar su formato. Si alguien manipulase manualmente el localStorage del navegador, podría introducir un valor CSS arbitrario. El impacto es solo estético — no ejecuta JavaScript. Requiere acceso físico al navegador ya autenticado.

triaje.html · l.332 
// Actual — asigColor viene de localStorage sin validar formato
const asigColor = COL_PERSONA[asig] || 'var(--borde)';
// ... luego en innerHTML:
`style="background:${asigColor}"`

// Corrección mínima:
const SAFE_COLORS = new Set(['#f0a431', '#7fd1c1', '#f2a7b8']);
const asigColor = SAFE_COLORS.has(COL_PERSONA[asig])
  ? COL_PERSONA[asig] : 'var(--borde)';

R1 Sin ninguna media query en la hoja de estilos
Crítico

La búsqueda de @media en css/styles.css no devuelve ningún resultado. Todas las dimensiones son fijas para escritorio. En dispositivos menores de ~900 px, los layouts de grid y el sidebar fixed rompen la interfaz.

R2 Tabla necesita ~784 px mínimo; en móvil queda cortada silenciosamente
Crítico

La tabla de triaje.html tiene seis columnas con anchos fijos declarados en atributos style: 96 + 90 + 260 + 120 + 88 + 130 = ~784 px mínimos. El contenedor usa overflow: clip en lugar de overflow: auto, lo que corta el contenido desbordado sin mostrar scrollbar. El usuario no puede ver las columnas derechas ni sabe que existen.

triaje.html l.59–68 · css/styles.css l.549 (overflow: clip)
R3 Sidebar fixed de 232 px deja 143 px al contenido en un móvil de 375 px
Crítico

El sidebar tiene position: fixed; width: 232px y el contenido tiene margin-left: 232px. En un iPhone SE (375 px), el área disponible para toda la tabla, tarjetas y formularios es de 375 − 232 = 143 px. Ningún componente cabe en ese ancho.

css/styles.css l.255–267 (.sidebar-triaje)
R4 Grids de formulario no colapsan a una columna en móvil
Alto

.form-layout (usado en nuevo-ticket.html, cierre-ticket.html y detalle-ticket.html) declara grid-template-columns: 1fr 280px sin regla responsive. En móvil, el aside de 280 px se comprime junto al formulario principal dejando solo ~95 px para los campos de texto.

css/styles.css l.828 (.form-layout)
R5 Grid de 3 cards no colapsa — ~47 px por card en móvil
Alto

.cards-resumen usa grid-template-columns: repeat(3, 1fr). Con el sidebar activo en móvil, el espacio disponible (143 px) dividido en 3 da ~47 px por tarjeta — completamente ilegible.

css/styles.css l.413 (.cards-resumen)
R6 Panel inline de 320 px comprime la tabla en tablet
Medio

Cuando se selecciona un ticket, el panel lateral aparece con width: 320px; flex-shrink: 0. En tablet (768 px − 232 px sidebar = 536 px), la tabla más el panel suman más del viewport disponible.

Arreglo 2 — Media queries (añadir al final de css/styles.css)

Mínimo de emergencia para que la app no rompa en móvil. No es el diseño responsive completo — oculta el sidebar en pantallas pequeñas y colapsa los grids a una columna.

css/styles.css — añadir al final 
/* ══ RESPONSIVE ════════════════════════════════ */

/* Tablet (≤ 900 px): ocultar sidebar, scroll horizontal en tabla */
@media (max-width: 900px) {
  .sidebar-triaje    { display: none; }
  .triaje-contenido  { margin-left: 0; }
  .cards-resumen     { grid-template-columns: 1fr 1fr; }
  .panel-detalle     { display: none; }
  .contenedor-tabla  { overflow-x: auto; } /* scroll en vez de clip */
}

/* Móvil (≤ 600 px): colapsar todos los grids a una columna */
@media (max-width: 600px) {
  .cards-resumen     { grid-template-columns: 1fr; }
  .form-layout       { grid-template-columns: 1fr; }
  .detalle-layout    { grid-template-columns: 1fr; }

  .header-busqueda   { width: 130px; }
  .header-busqueda:focus { width: 160px; }

  .pagina-contenido  { padding: 18px 16px; }
}

Glosario

Conceptos técnicos de este informe

XSS (Cross-Site Scripting)
Ataque en que texto malicioso introducido por un usuario se ejecuta como código HTML/JavaScript al pintarse en la pantalla. Se previene escapando los caracteres especiales antes de insertarlos en el DOM.
localStorage
Almacén de datos del navegador, por dominio, persistente entre recargas. No se envía al servidor. Todas las mutaciones de estado de esta app (cambios de estado, asignaciones, tickets nuevos) se guardan aquí.
innerHTML vs textContent
innerHTML interpreta el contenido como HTML — peligroso si recibe texto sin escapar. textContent inserta texto literal sin interpretar etiquetas — siempre seguro.
fetch()
Función de JavaScript que hace peticiones HTTP. Requiere que el archivo esté servido desde un servidor, no abierto como file:// en el disco local.
Media query
Regla CSS que aplica estilos solo cuando la pantalla supera o no llega a cierto ancho. Base del diseño responsive. Ejemplo: @media (max-width: 600px) { ... }
overflow: clip
Valor CSS que corta el contenido que desborda el contenedor, sin mostrar scrollbar. En esta app, oculta silenciosamente las columnas derechas de la tabla en pantallas pequeñas.
Surge.sh
Plataforma de alojamiento de webs estáticas. Sirve todos los archivos del directorio publicado tal cual, sin backend ni base de datos. El archivo .surgeignore le indica qué excluir.
Código huérfano
Archivo o función que existe en el repositorio pero que ninguna otra parte del código carga o llama. No afecta al usuario final, pero confunde a quien lee el proyecto.
